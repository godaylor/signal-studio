## License and provenance: non-negotiable

- Never delete, replace or truncate root `LICENSE`.
- Preserve `Copyright (c) Umami Software, Inc.` and the full MIT notice.
- Preserve explicit language that the transformed product is based on Umami.
- A new product copyright may be added separately; it must not erase upstream attribution.
- Rebrand product UI/metadata without implying rights to the Umami name or logo.
- Do not add fonts, icons, maps, datasets, browser bundles or dependencies without recording license/provenance when the relevant milestone introduces that process.
- Treat GeoLite2, DiceBear styles, maps/flags/icons, `ua-parser-js@2`, rrweb bundles and `@umami/react-zen` as unresolved provenance items until verified.
- Distribution images/archives must eventually contain `LICENSE` and third-party notices.

## Scope discipline

- Work on one named `PLAN.md` milestone or a smaller explicitly requested task.
- Keep changes inside that milestone's declared subsystems.
- Do not bundle opportunistic refactors with feature work.
- Do not rewrite `src/queries/sql`, tracker, recorder or the whole route tree for consistency alone.
- Preserve backward-compatible tracker/ingestion behavior unless a versioned change is explicitly approved.
- Use the strangler approach: add a working vertical slice, verify it, then retire legacy paths deliberately.
- Do not introduce microservices merely to demonstrate architecture.
- PostgreSQL is the reference backend. Do not claim ClickHouse support for a new query without parity tests.

## Existing worktree safety

- Existing uncommitted changes belong to the user unless clearly created by the current task.
- Never discard or overwrite unrelated changes.
- Inspect `git status --short --branch` before and after work.
- Avoid destructive git commands.
- If generated commands modify tracked files, verify the diff and restore only changes known to have been generated by the current task.
- Do not delete databases, volumes, containers or artifacts without resolving the exact target and confirming it is task-owned.

## Architecture rules

- New UI features call typed hooks/API clients, not Prisma or raw query modules.
- Route handlers stay thin: parse → authenticate → enforce assurance → authorize → service → response.
- Permission logic lives in reusable server-side permission services.
- New analytics use the versioned normalized `AnalysisQuery` contract.
- Shareable analytical state belongs in the URL codec; server data belongs in TanStack Query; ephemeral drafts remain local.
- Do not store the same authoritative state independently in URL, Zustand and component state.
- An Insight owns its query; dashboard widgets reference Insights.
- Application `User` and product `TrackedUser` are different domain types.
- Cache keys include tenant/project, normalized query, adapter/exactness and permission-sensitive scope.
- Realtime UI consumes a timestamped snapshot contract even if transport is polling.
- Large exports are streamed/paged/background jobs, not unbounded in-memory ZIPs.

## Data and analytics semantics

Every new metric/query must define:

- unit of analysis;
- numerator/denominator;
- user/account/session/visit identity;
- exact or approximate behavior;
- timezone and interval;
- half-open range `[start, end)`;
- filter and segment semantics;
- late-arriving event behavior where relevant;
- deletion/retention behavior.

Requirements:

- Use parameterized SQL/query APIs.
- Enforce date, page-size, cardinality and step-count bounds.
- Prefer cursor pagination for chronological entity/event lists.
- Do not perform mandatory expensive total counts unless the product needs them.
- Do not optimize away semantic correctness.
- Add golden-data tests before changing funnel, retention, identity or exactness behavior.
- Expose freshness/definition/exactness in analytical result contracts.

## Security rules

The baseline contains open security findings. Do not copy them into new code.

- Required 2FA must be enforced in the common server auth guard.
- Full auth/share tokens need explicit type, audience, issue time, expiry and revocation/version behavior.
- Logout/password changes must revoke applicable sessions.
- Rate-limit login and sensitive verification routes.
- `APP_SECRET` must not silently fall back to `DATABASE_URL` in production target behavior.
- Public ingestion CORS and management API CORS are separate policies.
- Recorder/cache tokens are bound to token type, project/website and session context.
- Public shares are scoped, expiring and revocable against a live record.
- Authorization is never implemented only by hidden navigation or disabled controls.
- Replay, sensitive traits, export and public sharing are separate capabilities.
- Never log secrets, tokens, raw sensitive traits or replay payloads.
- Do not expose stack traces in user-facing errors.

## Frontend and product design rules

Signal Studio is a product intelligence workspace for PLG teams, not a generic admin dashboard.

- Keep the primary IA: Home, Explore, Dashboards, Audiences, Experience, Live.
- Treat Website as a Source under data management, not the main product object.
- Preserve the distinctive Query Spine concept for analytical lineage.
- Spend visual boldness on the Query Spine; keep surrounding UI precise and restrained.
- Avoid decorative gradient blobs, card nesting and unnecessary pills.
- Tables are first-class analytical surfaces.
- Large KPI typography is used only when the number drives a decision.
- Use copy from the user's perspective: `Save insight`, not `Submit`.
- Keep action names consistent between button, toast and audit event.
- Loading, empty, error, partial, stale and permission states are required product states.
- Responsive behavior must be designed, not achieved by shrinking desktop UI.
- Mobile complex query editing may use a full-screen step flow.
- Respect reduced motion.

## Accessibility rules

Target WCAG 2.2 AA for flagship routes.

- Use semantic buttons/links/inputs; no clickable `div` or icon-only `onClick` without full semantics.
- Every icon-only action needs an accessible name.
- Keep visible keyboard focus.
- Drawers/dialogs trap and restore focus.
- Color is not the only data encoding.
- Charts need an accessible summary and equivalent data table when applicable.
- Dense matrices/tables need documented keyboard navigation.
- Live updates use restrained ARIA announcements.
- Add component accessibility tests and Playwright/axe coverage for new flagship screens.

## Performance rules

- Name the dataset and environment for every performance claim.
- Track p50/p95, query duration and rows/bytes scanned where available.
- At the reference 1M-event dataset, use budgets from `TRANSFORMATION_SPEC.md`.
- Prevent duplicate dashboard queries across widgets.
- Cancel superseded requests.
- Bound breakdown cardinality, date range and page size.
- Use short server cache/single-flight for compatible analytics.
- Hidden tabs must reduce or stop live polling.
- Lazy-load replay/player and other heavy feature bundles.
- Measure before adding indexes, rollups or materialized views.

## Observability rules

New server flows should support:

- structured logs;
- request/query/job IDs;
- safe error codes;
- latency/outcome metrics;
- dependency-aware readiness;
- ingestion accepted/rejected/lost counters;
- query cache/scanned-work metrics;
- export/live/retention job state.

Do not use `/api/heartbeat` returning `{ok:true}` as proof that dependencies are ready.

## Testing rules

For every changed behavior, select the smallest sufficient layers:

- unit: codecs, schemas, definitions, transforms and permissions;
- component: interactions, states and accessibility;
- PostgreSQL integration: migrations, services and analytical queries;
- API integration: auth → permission → service;
- Playwright: critical user workflow;
- performance: expensive query/realtime/export changes;
- ClickHouse parity: only when enabling that adapter capability.

Test isolation requirements:

- no shared fixed usernames/entity IDs across parallel tests;
- retries must be idempotent or reset their state;
- each test cleans or owns its data;
- do not assert sensitive fields such as password hashes in API responses;
- use accessible locators before test IDs where practical.

## Baseline commands

M0 established one supported local and CI contract: Node `22.22.x` (pinned to
`22.22.2`) and pnpm `10.15.1` through Corepack. `.npmrc` enforces the Node
engine, while `.nvmrc`, `package.json`, CI and Docker use the same versions.

Install and initialize local configuration:

```powershell
corepack enable
corepack prepare pnpm@10.15.1 --activate
pnpm install --frozen-lockfile
pnpm env:init
```

`pnpm env:init` creates `.env` once with random application and 2FA secrets; it
does not overwrite an existing file. Do not copy placeholder values from
`.env.example`.

Start PostgreSQL, migrate, seed, build and run the standalone application:

```powershell
docker compose up -d db
pnpm db:migrate
pnpm admin:bootstrap --local
pnpm db:seed
pnpm build
pnpm start
```

`pnpm db:migrate` and `pnpm db:seed` are explicit, repeatable steps. Build and
startup never apply migrations. Build copies `public` and `.next/static` into the
standalone output, and `pnpm start` always enables production validation before
loading `.next/standalone/server.js`.

Verification:

```powershell
pnpm typecheck
pnpm lint
pnpm test
pnpm exec playwright install --with-deps chromium
pnpm test:e2e
```

Notes:

- `DATABASE_URL` is required for Prisma generation and tests; `pnpm env:init`
  supplies the compose-compatible local value.
- GeoLite2 is skipped by default. A download occurs only when an operator
  explicitly configures a licensed `GEO_DATABASE_URL` or `MAXMIND_LICENSE_KEY`.
- Local compose builds the current checkout and uses a one-shot migration
  service; it does not pull an upstream application image.
- `/api/heartbeat` is shallow liveness; `/api/ready` checks PostgreSQL readiness.
- Playwright E2E requires its Chromium browser installation.
- `pnpm check` writes fixes; use `pnpm lint` for read-only lint verification.

## Milestone completion report

When completing a milestone, report:

1. user-visible outcome;
2. exact files/subsystems changed;
3. migrations/config changes;
4. commands and results;
5. test counts and accepted exclusions;
6. measured performance against the named dataset;
7. security/accessibility/permission checks;
8. remaining risks and follow-ups;
9. confirmation that `LICENSE` and attribution remain intact;
10. git status and any unrelated pre-existing changes preserved.

Do not mark a milestone complete because files were added. Mark it complete only when its `PLAN.md` definition of done is satisfied end-to-end.
